Rentra — detailed end-to-end project flow

Follow each flow from the screen a person uses, through API/security and business rules, to database writes and service responses. Dashed connectors mark a planned or currently unavailable integration.

Web app

Full marketplace experience in React + TypeScript + Vite. Screen → API helper/Axios → backend. Access token is attached to protected API calls.

Mobile app

Expo/React Native with register/login and tenant, landlord, admin home shells. It uses the same API; most detailed rental workflows remain web-first.

Backend + database

NestJS/Express routes under /api. Guards and DTO validation run before feature services. Prisma maps service reads/writes to PostgreSQL.

Current limits to know

Payment module has no provider adapter registered. AI FastAPI only has /health. Fake Detector is a confirmed-report view, not automated AI.

How to read

Each numbered diagram is one complete sequence. Database cylinders are persisted records; external provider boxes are outside PostgreSQL; dashed arrows are future/unavailable links.

One schema, one source of truth

Prisma schema and migrations live under packages/database/prisma. Backend business rules decide whether a record can be created or its status can change.

AI roadmap is separate

Possible future model use: fraud-risk cues, rent estimate, listing search ranking, document triage. Keep suggestions explainable and let a human admin review consequential decisions.

2. Register, log in, and get role access

flowchart TD
  C[Web or mobile: register] --> R[POST /api/auth/register]
  R --> CHECK[Backend checks existing email/phone/CNIC]
  CHECK --> HASH[Hash password + one-time code]
  HASH --> PENDING[(PendingRegistration in PostgreSQL<br/>default role TENANT · code expires in 10 min)]
  PENDING --> MAIL[EmailService sends registration code via Gmail SMTP]
  MAIL --> CODE{User enters valid code?}
  CODE -- no / expired --> RETRY[Reject; retry limits / resend flow apply]
  CODE -- yes --> VERIFY[POST /api/auth/register/verify]
  VERIFY --> USER[(Create verified account<br/>TENANT role initially)]
  USER --> TOKEN[Issue access + refresh tokens]
  TOKEN --> STORE[Client stores session<br/>web storage / native SecureStore]
  STORE --> ROUTE[Protected route loads role capabilities]
  C2[Web or mobile: login] --> LOGIN[POST /api/auth/login]
  LOGIN --> PASS{Password correct<br/>and account active?}
  PASS -- no --> DENY[Reject login]
  PASS -- yes --> OTP[Send EMAIL_LOGIN code by email]
  OTP --> OTPVERIFY[POST /api/auth/login/verify]
  OTPVERIFY --> TOKEN
  ROUTE --> TENANT[Tenant workspace]
  ROUTE --> LANDLORD[Landlord workspace<br/>capability added after property posting/role update]
  ROUTE --> ADMIN[Admin workspace<br/>admin-only management routes]

3. Landlord adds a property; admin verifies it; tenants discover it

flowchart TD
  OWNER[Landlord fills property/listing form] --> API1[Web API helper sends authenticated request]
  API1 --> RULES[Backend validates ownership, coordinates,<br/>location and property/listing fields]
  RULES --> CREATE[(Prisma transaction / PostgreSQL<br/>property + linked listing + details<br/>initially pending/unpublished)]
  OWNER --> PHOTO[Upload property photos]
  PHOTO --> UPLOAD[Backend validates image and sends bytes to Cloudinary]
  UPLOAD --> IMG[(Save secure image URL + metadata in PostgreSQL)]
  CREATE --> QUEUE[Verification/admin review queue]
  IMG --> QUEUE
  QUEUE --> DOCS[Owner supplies verification evidence URLs<br/>identity / host / property evidence]
  DOCS --> REVIEW[Admin reviews evidence and records notes]
  REVIEW --> APPROVED{Identity and host checks approved?}
  APPROVED -- no --> REJECT[Reject or request updates<br/>record decision + audit event + notification]
  APPROVED -- yes --> PUBLISH[Set property ACTIVE;<br/>linked listing PUBLISHED]
  PUBLISH --> SEARCH[Tenant browse/search/filter/nearby<br/>availability and listing details from API]
  SEARCH --> SAVED[Optional: favorite or saved search]
  SEARCH --> REQUEST[Tenant submits rental request<br/>phone verification required]

4. Tenant request, booking, agreement and payment limits

flowchart TD
  START[Tenant chooses a property or listing] --> KIND{Rental flow}
  KIND -- long-term rental request --> REQ[Create request after phone check<br/>verify property is active; prevent duplicate active request]
  REQ --> NOTIFY[Persist request + notify landlord]
  NOTIFY --> DECIDE{Landlord response}
  DECIDE -- decline --> DECLINED[Request REJECTED; tenant notified]
  DECIDE -- accept --> AGREE[Accept request in transaction]
  AGREE --> ACTIVE[Create ACTIVE rental agreement<br/>request becomes ACCEPTED]
  ACTIVE --> RENTPAY[Payment records / rent collection endpoints]
  KIND -- short stay booking --> BOOK[Create booking after phone check<br/>validate dates, active property and availability]
  BOOK --> LOCK[Database transaction + advisory lock<br/>avoid overlapping inventory bookings]
  LOCK --> HOLD[Create booking/payment state<br/>notify tenant and property owner]
  HOLD --> CHECKOUT{Real payment adapter configured?}
  RENTPAY --> CHECKOUT
  CHECKOUT -- no; current setup --> UNAVAILABLE[No gateway adapter is registered<br/>real checkout/verification/refund unavailable]
  CHECKOUT -- after provider is integrated --> PROVIDER[Provider initiate → webhook/verify<br/>idempotent payment status update]
  PROVIDER --> COMPLETE[Update booking/agreement/payment state<br/>receipt/status is available in product]
  ACTIVE --> END[Participants manage agreement lifecycle<br/>and may terminate through API]

5. Messages, notices, support tickets, moderation

flowchart TD
  CHAT[Landlord ↔ tenant chat] --> MSG[Authenticated message API]
  MSG --> SAVE[(Conversation + Message in PostgreSQL)]
  MSG --> NEWMSG[Recipient gets unread count / message notification]
  READ[Recipient opens conversation] --> MARK[Mark delivered/read timestamps and state]
  MARK --> SAVE
  USER[User submits Help & Support ticket] --> LIMIT[Backend checks ticket limits and account restrictions]
  LIMIT --> NEW[(Create ticket status NEW<br/>user sees Not opened)]
  NEW --> ADMININBOX[Admin inbox shows NEW ticket bold]
  ADMININBOX --> OPEN[Admin opens ticket → status OPEN<br/>user sees Opened / waiting for admin]
  OPEN --> REPLY[Admin replies → status PENDING<br/>user notified in app]
  REPLY --> USERREPLY[User replies → status OPEN]
  USERREPLY --> REPLY
  REPLY --> RESOLVE[Admin resolves → RESOLVED]
  PROFILE[Admin opens a user profile] --> NOTICE[Send Notice: choose reason + write message]
  NOTICE --> NOTICECHAT[Create/use Rentra Support chat<br/>message appears in user's message inbox]
  NOTICECHAT --> UNREAD[Unread badge/notification; user can read<br/>official notice inbox is not reply-enabled]
  ADMINACTION[Admin moderation / warning / restriction] --> AUDIT[(Audit event + notification where applicable)]
